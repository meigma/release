## 2026-08-16 21:59 — Initial automation structure
The working direction is one centrally governed release DAG per producer profile, not independent release-type workflows that each rebuild. A language-specific build job should produce one immutable release bundle containing distributable files, `checksums.txt`, SBOMs, and a machine-readable manifest tied to the tag and commit. Optional publisher jobs then consume and verify that bundle without compiling source.
Reusable workflows should own runner boundaries, matrices, permissions, secrets, publication, and attestations. Composite actions should be reserved for repeated step-level mechanics inside jobs. Repositories should use a thin caller workflow and select supported publishers through explicit inputs.
Likely producer profiles are Go, Python, and later specific IaC deliverable types; IaC is not one coherent build profile. GitHub Releases, OCI packaging, and package-manager metadata can share the same release bundle, but distributed publication cannot be truly atomic. Publishers must therefore be idempotent and the GitHub Release should remain a draft until required publication and attestation stages succeed.
Open issues for channel research: whether MacPorts and Nix should intentionally rebuild from source or consume authoritative binaries; which channels are required versus optional for finalization; and the exact release-bundle manifest schema.

## 2026-08-16 22:11 — Draft release and source package boundaries
GitHub explicitly recommends creating a draft, attaching all assets, and only then publishing when immutable releases are enabled. The candidate workflow should therefore build and validate first, then create or reconcile the exact draft release and upload assets. Initial automation should stop with a reviewable draft rather than automatically crossing the irreversible publication boundary.
Manual publication can become the promotion signal. A later `release.published` workflow may perform retryable distribution work, while candidate-stage automation should avoid irreversible external writes. OCI publication ordering remains an open design choice because publishing it before approval creates a separate irreversible surface, while publishing after approval allows temporary channel skew.
Nix is reclassified as repository scaffolding rather than a release asset: provide and validate a `flake.nix`, let users consume tagged Git source, and do not assume nixpkgs upstreaming.
MacPorts conventionally consumes source through a Portfile and its `golang` PortGroup runs `go build`; MacPorts then creates its own binary archives where applicable. Treat MacPorts as source-package metadata rather than a consumer of Meigma's canonical release binaries. Without upstreaming, distribution would also require a custom ports tree and `PortIndex`.

## 2026-08-16 22:41 — mkosi and OBS interoperability research
Parallel research confirmed that mkosi and Open Build Service are actively interoperated, but primarily for OS images rather than application OCI images. OBS has recognized `Type: mkosi` as a native recipe since 2022, with compatibility work merged in February 2026. ParticleOS is the clearest live example: GitHub/OBS workflows import mkosi configuration, OBS builds offline against its prepared package mirror, and current signed EFI, raw disk, ESP, verity, manifest, and checksum outputs are published from `system:systemd`.
mkosi is principally a distro-aware OS image assembler. Current mkosi supports `Format=oci`, introduced in April 2024, and emits a single-platform, single-layer OCI Image Layout directory with labels and annotations. It neither pushes to registries nor aggregates multi-platform indexes; those require external OCI tooling.
The native OBS mkosi adapter cannot currently publish that OCI format. `build-recipe-mkosi` writes outputs under `OTHER` and deletes directory outputs because OBS cannot publish them. It also lacks the `DOCKER` result directory and `.containerinfo` metadata used by OBS's registry publisher. No live public `Type: mkosi` plus `Format=oci` pipeline was found. Native OBS registry paths are Dockerfile with Podman or KIWI.
OBS does provide draft-like promotion semantics independently of mkosi: build and publish flags are separate, and a manual release target can copy completed sources and binaries without rebuilding into a build-disabled publication project. For containers the target publisher may reconstruct manifests and indexes, so the promoted top-level OCI digest is not documented as identical and must be verified.
Decision direction: mkosi plus OBS is viable for future OS, UKI, sysext, or appliance delivery. It is not the recommended application-OCI path for Meigma today. If OBS is adopted for Go application OCI, use its Dockerfile/Podman or KIWI adapter and manual release targets; otherwise retain a GitHub-centered OCI publisher. The final target registry digest remains the attestation subject.
Primary references: https://openbuildservice.org/help/manuals/obs-user-guide/cha-obs-package-formats#sec-pkgfmt-mkosi, https://github.com/openSUSE/obs-build/blob/master/build-recipe-mkosi, https://github.com/systemd/mkosi/blob/main/mkosi/resources/man/mkosi.1.md#output, and https://github.com/systemd/particleos.

## 2026-08-17 07:50 — apko and melange research
Verdict: apko is a strong candidate for Meigma's daemonless application-image composer, with melange as the necessary adapter that turns the already-built Linux executable into an APK. This preserves the build-once rule if melange only copies the canonical binary into the package and does not compile or strip it. The proposed byte path is `canonical Linux binary -> architecture-specific APK -> apko OCI layout -> registry`; the experiment must compare the executable digest at every boundary.

apko is declarative and has no Dockerfile `RUN` equivalent. It resolves and verifies APK repositories, lays out package contents without running package scripts by default, emits single- or multi-architecture OCI images, generates SPDX image SBOMs, and can either write an OCI Image Layout directory or publish directly through `go-containerregistry`. `apko publish` returns the final digest and can write all published references to a file. A lockfile generated by `apko lock` is required for our reproducibility claim: the YAML alone still resolves against mutable repository indexes, while the lock records exact package versions and checksums.

apko cannot add an arbitrary release binary directly; custom files must first be packaged as APKs. melange supplies that package boundary, can generate and sign a local repository index, creates package SBOMs, supports fixed build timestamps, and can run a minimal pipeline that installs a prebuilt file from `--source-dir`. This is more machinery than a Dockerfile `COPY`, but it gives apko a complete package inventory and avoids an opaque mutation layer. Do not use melange's Go pipelines here: compiling again would violate the authoritative-artifact invariant.

The “non-daemon” description needs qualification. apko itself writes or pushes images without a Docker daemon. melange requires an execution runner for pipeline commands: current choices are Bubblewrap, Docker, and QEMU. Bubblewrap avoids a container daemon, but GitHub's `ubuntu-latest` requires privileged host setup to relax AppArmor's unprivileged-user-namespace restriction. The official setup action uses `sudo` to install an AppArmor profile and reload it. Thus this path is daemonless, not privilege-free.

Supply-chain controls remain the outer workflow's responsibility. apko verifies APK repository signatures unless explicitly disabled and generates SBOM files, but it does not sign the final OCI digest or emit SLSA provenance. melange's opt-in provenance is an in-toto SLSA v1 statement beside each APK and can be APK-key signed; however, it contains the package configuration and final APK digest but no resolved dependencies, and its builder ID is hard-coded to a Chainguard URL even for self-run builds. Treat it as package metadata, not evidence of a Meigma SLSA level. The central GitHub workflow should attest the final OCI digest and image SBOM with GitHub's attestation actions and sign the digest with Cosign if registry consumers require that verification path.

Chainguard coupling is acceptable but real. Both projects are Apache-2.0, actively maintained, and released frequently; as of this check apko was v1.2.37 and melange v0.59.1, with both repositories and Wolfi receiving changes today. The tools can consume Alpine or a Meigma-local APK repository and do not require Chainguard's commercial service. Coupling remains in project governance, Go module paths, public installation images, documentation, APK conventions, and melange's provenance identifiers. melange is still pre-1.0, and apko's README continues to call the project a work in progress. Pin exact tool versions.

Do not adopt the existing convenience actions as the trust boundary. `chainguard-dev/actions/apko-build` declares itself deprecated, while `setup-melange` defaults to the latest release and downloads a tarball through `curl | tar` without verifying its supplied Cosign signature. apko and melange releases provide checksums plus `.sig` and `.crt` assets. A Meigma workflow should download fixed versions and verify their release signatures against the exact upstream GitHub Actions workflow identity before execution.

Candidate direction: build the APK and apko OCI layout during the reversible candidate run, upload the layout, lockfile, and SBOMs as immutable workflow artifacts, and inspect them before release approval. After `release.published`, push that exact layout rather than rebuilding it, resolve the registry digest, and attest it. This avoids publishing a candidate tag before human approval and avoids post-approval recompilation. The next prototype must prove that the selected layout-to-registry tool preserves the apko index digest, that the image executable equals the canonical release binary, and that amd64/arm64 images run correctly.

Primary references: https://github.com/chainguard-dev/apko/blob/main/README.md, https://github.com/chainguard-dev/apko/blob/main/internal/cli/build.go, https://github.com/chainguard-dev/apko/blob/main/internal/cli/publish.go, https://github.com/chainguard-dev/melange/blob/main/README.md, https://github.com/chainguard-dev/melange/blob/main/docs/md/melange_build.md, https://github.com/chainguard-dev/melange/blob/main/pkg/build/slsa.go, and https://github.com/chainguard-dev/melange/blob/main/.github/actions/setup-bubblewrap/action.yaml.

## 2026-08-17 10:00 — Native Linux packages
Add DEB and RPM to the Go delivery contract. They should be candidate-stage derivations of the same canonical Linux executables, built before the draft release is published. Use GoReleaser's nFPM pipe initially: it consumes selected GoReleaser build IDs rather than compiling again and can emit DEB, RPM, and APK packages for each Linux architecture from one package definition. This also creates a simplification opportunity for the OCI path: use nFPM for the intermediate APK and retain melange only if its repository-index or embedded-SBOM behavior proves necessary. nFPM itself is a cross-platform, zero-runtime-dependency packager and does not generate package-repository metadata.

Separate package creation from repository publication. Candidate outputs include the `.deb` and `.rpm` files, checksums, SBOMs, signatures where applicable, and GitHub attestations; they can also be GitHub Release assets. After `release.published`, publisher adapters update the external APT and RPM repositories using those exact package bytes. APT's primary trust boundary is signed `InRelease`/`Release` repository metadata rather than an individual `.deb`; RPM normally uses an embedded package signature as well as signed repository metadata. The RPM package signature therefore belongs in candidate construction, while both repositories' mutable indexes are promotion-stage outputs.

This does not cover Debian, Fedora, or other official distribution repositories. Those ecosystems normally rebuild source under distribution control and should be treated as separate source-package/upstreaming tracks, like MacPorts and Nix, rather than consumers of Meigma's canonical binary packages.

Primary references: https://goreleaser.com/customization/nfpm/ and https://nfpm.goreleaser.com/docs/configuration/.

## 2026-08-17 10:43 — mise PATH resolution
The historic shadowing problem reproduces in the `mvp` worktree. The agent process inherits `MISE_SHELL=zsh`, so `mise doctor` reports `activated: yes`, but the actual non-interactive PATH contains neither mise's shims nor its computed install directories. `shims_on_path` is `no`. Bare `golangci-lint` therefore resolves `~/.local/bin/golangci-lint` 2.11.4 instead of the project pin 2.12.2; bare `moon` resolves `~/.proto/bin/moon` 2.3.5 instead of 2.5.1.

The local `.zshrc` correctly runs `mise activate zsh`, but activation updates direct tool paths through prompt and directory-change hooks. Agent subprocesses start non-interactively and receive their working directory after shell initialization, so that hook does not repair PATH. `mise exec --` is deterministic: it prepends every project install directory, resolved golangci-lint 2.12.2 and Moon 2.5.1, and exported `GOTOOLCHAIN=local`. Prepending `~/.local/share/mise/shims` also resolved 2.12.2 inside the project, but fell through to 2.11.4 outside it; shims resolve from the current directory and do not provide the full mise environment contract.

CI has two distinct behaviors. The template pins `jdx/mise-action` v4.2.0, which adds the mise binary and shim directory through `GITHUB_PATH`; this is normally enough for later steps but remains working-directory- and PATH-order-dependent. Current v4.2.5 (`3c2e0cf82a5b2e5249f0d3635a4d83d0ae861518`) additionally exports the direct PATH computed by `mise env`, preserving order through `GITHUB_PATH`, while still adding shims and automatically using `mise install --locked` when a lockfile exists.

Decision direction: PATH is a convenience, not the automation contract. Agents, scripts, and workflows should enter through `mise run <task>` or `mise exec -- <command>`. CI should pin mise-action v4.2.5 or newer with `export_path: true`, then still invoke the top-level task runner through `mise exec --`; this remains correct if a later action prepends another tool. Local non-interactive convenience may add `mise activate zsh --shims` to `.zprofile`, but it cannot replace `mise exec` because shim resolution depends on the current directory and omits `[env]` behavior. When Moon is added, verify a child task reports the pinned Go and golangci-lint versions rather than assuming `toolchains.default: system` preserves PATH.

## 2026-08-17 12:19 — Reusable Go CI prototype
Extracted the CI implementation to `.github/workflows/go-ci.yml` with a `workflow_call` trigger. The reusable contract deliberately has no inputs or secrets: a caller provides the standard `mise.toml`, `mise.lock`, `moon.yml`, `.golangci.yml`, and Go module, and the workflow checks out and tests the caller repository. The repository-facing `.github/workflows/ci.yml` now contains only event filters, concurrency, read-only permissions, and a same-commit local call to `./.github/workflows/go-ci.yml`.

For external consumers, the corresponding call will be `meigma/release/.github/workflows/go-ci.yml@<full-commit-sha>`; no branch reference should be documented as the default. GitHub's reusable-workflow execution retains the caller repository context, so the checkout in the shared workflow retrieves the caller rather than `meigma/release`.

The prototype was tested on GitHub, not only parsed locally. A temporary `mvp` push trigger ran caller workflow `CI` against reusable job `ci / ci`; Actions run 32059599766 completed successfully in 55 seconds, including locked mise setup, caches, and `mise exec -- moon ci --summary minimal`. ## 2026-08-17 12:40 — Independent CI review
A read-only DevOps review found the MVP sound: exact action SHAs and matching version comments, least-privilege permissions, checkout credentials removed, locked and provenance-verified mise installation, explicit `mise exec` boundaries, valid Moon configuration, correct full-history checkout, effective format/lint/build/test gates, and a successful real reusable-workflow run.

Two concrete defects deserve early fixes. First, `moon.yml` and `.github/workflows/**` are not task inputs; a PR changing only the gate can make `moon ci` report no affected tasks and exit zero. Add the gate-defining files to the affected input surface. Second, Moon 2.5.1 lacks a `macos-x64` entry in `mise.lock` despite the requested four-platform lock and an available upstream Intel macOS artifact.

Useful hardening candidates: set a job timeout, consider `ubuntu-24.04` instead of `ubuntu-latest`, avoid canceling in-progress `main` push runs, add `filter: blob:none` to the required full-history checkout, and separate CI-only mise tools from the larger release toolchain to reduce the approximately 290 MB cold cache. The rolling `github.run_id` build/lint cache keys trade freshness for continuous cache churn and should be revisited once run data exists. Dependabot and CODEOWNERS belong in later repository-hardening work.

Do not add speculative reusable-workflow inputs yet. Optional inputs can be added backward-compatibly when a real consumer needs variation; the current no-input contract is intentional. The first external consumer must still test caller-repository checkout semantics, repository Actions access policy, and its required standard files.
